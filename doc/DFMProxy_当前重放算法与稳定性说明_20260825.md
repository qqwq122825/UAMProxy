# DFMProxy 当前重放算法与稳定性说明

**版本**：v1.0（2026-08-25）  
**对应实现**：DFMProxy v1.130.2 / `v130.2-player-device-pool-r1`

> 本文描述当前项目的通用方法。其他游戏的 `message_id`、`recordCode`、长度和周期会变化，但可以复用同一套分层、归组、补齐、保序和回溯流程。

## 1. 总体设计

DFMProxy 不直接循环发送旧密文，而是把 01 报告解析为报告和叶子，在当前 Live 数据、玩家录制池和中央模型之间做语义重建。

核心不变量：

```text
Live 当前数据优先
缺失部分才补
slot 与 recordSequence 连续
未知结构原样保留并可回溯
```

处理链：

```text
01/33 连接
  → 用户、游戏ID、设备和42B会话识别
  → 录制池/设备池/中央模型选择
  → Type9 report/leaf 解析
  → central9 + central_strong + player_same_device 补齐
  → 二级热规则
  → 序号、slot、容器和身份校验
  → output 发送
```

主要模块：

| 模块 | 作用 |
|---|---|
| `core/server.py` | 连接、01 流程、游戏 ID 绑定、重连和输出调度 |
| `core/replay_session_v130.py` | 42B 会话快照、续连候选和首个 Live 确认 |
| `core/crypto.py` | Type9 解析、重建、序号偏移和输出校验 |
| `core/type9_shadow.py` | input/template/shadow/output 四阶段重建 |
| `core/type9_special_rules.py` | 热规则、Live 修补、模板替换和空叶 |
| `core/pool.py` | 录制池、设备池和游戏 ID 降级池 |
| `ui/views.py` | 连接表、重放阶段、覆盖率和进度 |

## 2. 模板选择

当前默认选择顺序：

```text
同设备特征匹配
    ↓ 未命中
按游戏ID匹配
    ↓ 未命中
中央模型 + Live 透传/二级规则
```

设备上下文可包括 model、hardware_model、system_version、device_idfv、resolution、app_version、system_name 和 app_mach_uuid。

同设备录制池可以供同设备的其他账号复用；跨设备时，设备相关动态消息按匹配程度降级，中央固定层仍可使用。

当前 v1.130.2 样本使用 `player_only`：

```text
official_01_count = 0
personal_01_count = 172
```

## 3. 单报告重建

每个输入报告按以下顺序处理：

1. 解析 `recordCode`、`message_id`、长度、`recordSequence`、`logical_slot` 和动态字段。
2. 以 `message_id@slot#subtype` 建立当前报告集合。
3. Live 当前 slot 优先；模板只补缺失键。
4. 处理中央固定层、强检条件层和同设备动态层。
5. 应用热规则并标记每个叶子的来源。
6. 重建当前序号、slot、父容器和长度。
7. 执行 output group、身份和序号校验。

### 3.1 8004 子类型

`0x8004` 按 9 个 subtype 分开判断：

```text
Live 有 4 片 → 只补另外 5 片
Live 有 9 片 → 本周期不补 8004
```

### 3.2 中央固定层

当前中央 9 类来自 manifest：

```text
8000 / 8002 / 8003 / 8004(9 subtype) / 800B
8020 / 8021 / 8025 / 8028
```

当前周期模型示例：

| ID | 首个 slot | 周期 |
|---|---:|---:|
| `0x8000`、`0x8002`、`0x8003`、`0x8020` | 30 | 600 |
| `0x8004` | 30 | 300 |
| `0x800B` | 30 | 900 |
| `0x8021` | 158 | 420 |
| `0x8025` | 30 | 单次/按模板 |
| `0x8028` | 30 | 240 |

## 4. 同设备动态层

当前玩家层分为：

```text
设备画像：8007 / 800F / 8023
会话动态：8024 / 800D / 802C
环境事件：800A / 800C / 8027 / 8029 / 802A / 802B
```

周期外推设置：

```text
至少两个连续周期样本后才建立候选
8007 = 600 slot
800D = 600 slot
802C = 600 slot
事件时间线策略 = single_pass
```

事件类消息不做无限机械外推，而是依据已观察到的时间线和到期点处理。

## 5. 强检条件层

### 5.1 `0x8C03`

触发文件：

```text
mrpcs_i_f.data + mrpcs_i_j.data
```

当前模型：

```text
首个候选 slot = 150
周期 = 120 slot
动态字段 = logical_slot@0x1A、round_counter@0x24
```

长样本已经观察到：

```text
150 → 270 → 390 → 510 → 630 → ...
```

### 5.2 `0x9100`

触发文件：

```text
mrpcs_i_v_tl.data + mrpcs_i_vv.data
```

当前模型：

```text
首个候选 slot = 600
周期 = 600 slot
动态字段 = logical_slot@0x1A
```

文件状态出现后先进入候选集合，达到周期和上下文条件才生成消息。强检样本中 `mrpcs_i_vv.data` 出现后，在 `slot=3000` 生成了 `0x9100`。

### 5.3 去重

强检和补数据统一使用：

```text
message_id@slot#subtype
```

作为去重键。迟到 Live 叶不会再次插入同一键；内置候选已经发送后，迟到叶按当前动作保留、修补或转为空结果。

## 6. 热规则和未知结构

规则动作：

| 动作 | 作用 |
|---|---|
| `patch_live` | 保留 Live 叶，只改明确字段 |
| `replace_template_nearest` | 使用同设备/同长度附近模板 |
| `empty_2000` | 需要抑制内容时保留合法叶和序号 |
| `pass_live` | 没有可靠映射时原样发送 |

计数类字段优先 `patch_live`；需要抑制叶时优先 `empty_2000`。`drop_leaf` 属于旧兼容动作，只有在父容器、序号压紧和偏移延续均打开时才适合使用；发布前应检查当前 manifest 是否仍有不需要的 `drop_leaf`。

未知结构通常表现为 `message_id=null` 的 `0x011223xx`、`0x010Axxxx` 或其他 body schema。它们会记录 `recordCode`、长度、原始 Hex hash 和上下文，并走 `PASS_LIVE`，不参与自动补齐。

## 7. 首次重放与续连重放

### 首次重放

```text
42B 加入
  → 游戏ID绑定
  → 建立新语义会话
  → 首个 Live 报告确认
  → 模式：首次重放
```

### 续连重放

```text
旧连接断开
  → 保存语义会话快照
  → 新连接收到相同42B会话值
  → RECONNECT_CANDIDATE
  → 首个 Live 叶序列连续
  → NETWORK_RECONNECT / continued=true
  → 模式：续连重放
```

判定字段：

- 游戏 ID 相同；
- 42B 会话值相同；
- 断开间隔在保留窗口内；
- 新首个 Live 叶序列向前连续；
- 设备上下文仍一致。

传输池游标可以在新 TCP 连接上从 0 重新取样，但语义层的设备上下文、已发状态、slot 周期和 Live 序列继续沿用。当前 UI 在首个 Live 确认后显示“首次重放”或“续连重放”。

## 8. 序号与 slot

三个字段的含义不同：

| 字段 | 含义 |
|---|---|
| `recordSequence` | 当前报告流中的叶序号 |
| `logical_slot` | 周期位置 |
| `report_index` | AI 日志的报告分组索引 |

输出时使用当前会话游标生成 `recordSequence`，使用周期模型生成 `logical_slot`，再写入新的报告分组。模板历史序号不直接覆盖当前连接序号。

稳定性目标：

```text
无重复 message_id@slot#subtype
无序号空洞
slot 不回退
父容器长度和叶数量一致
身份和设备上下文一致
```

## 9. AI 日志分析顺序

每次运行目录主要包含：

```text
manifest.json
record_sessions.jsonl / record_frames.jsonl / record_leaves.jsonl
record_reports.jsonl
replay_events.jsonl / replay_groups.jsonl / replay_leaves.jsonl
reconnect_events.jsonl
template_selection_events.jsonl
downlink_events.jsonl / stream_frames.jsonl
control_events.jsonl / anomaly_full.jsonl
```

建议顺序：

1. `manifest.json`：版本、规则 revision、配置开关和 schema。
2. `reconnect_events.jsonl`：首次加入或续连。
3. `replay_events.jsonl`：决策、注入数量、来源和校验。
4. `replay_groups.jsonl`：central9、central_strong、player_same_device。
5. `replay_leaves.jsonl`：input/template/shadow/output 对比。
6. `anomaly_full.jsonl`：未知结构的前后文。

发布级检查应满足：

```json
{
  "checks": {
    "all_output_groups_valid": true,
    "final_identity_check": true
  },
  "validation_errors": []
}
```

## 10. 其他游戏的适配方式

不要把 80xx 数字写死在调度器中。每个游戏建立自己的消息规格表：

```json
{
  "message_id": "GAME_MSG_ID",
  "record_code": "GAME_RECORD_CODE",
  "length": 0,
  "family": "central|player|strong|event",
  "first_slot": 0,
  "period": 0,
  "subtype_rule": "message_id@slot#subtype",
  "dynamic_fields": [],
  "trigger_files": [],
  "action": "pass_live"
}
```

适配步骤：

1. 采集正常长时样本；
2. 提取每种消息的 recordCode、长度、slot 和周期；
3. 标注静态字段、动态字段和设备字段；
4. 至少用两个连续周期确认外推；
5. 建立“文件状态 → 条件消息”的关联；
6. 未知消息先 `PASS_LIVE`；
7. 通过四阶段回溯和输出校验后再启用补齐。

这样更换游戏时只替换消息规格和字段解码器，录制池、设备池、续连、日志和校验框架保持不变。

## 11. 发布前稳定性清单

- [ ] 首次连接最终显示“首次重放”。
- [ ] 不退游戏断线后最终显示“续连重放”。
- [ ] 42B 会话值一致，首个 Live 叶序列连续。
- [ ] Live 已有叶不重复，中央层只补缺失消息。
- [ ] 同设备动态层至少有两个连续周期样本。
- [ ] 强检文件出现后，条件消息按 slot 生成。
- [ ] `8C03/9100` 动态字段和周期连续。
- [ ] 未知结构原样保留并写入 AI 日志。
- [ ] 没有重复叶、序号空洞和 slot 回退。
- [ ] `all_output_groups_valid=true`。
- [ ] `final_identity_check=true`。
- [ ] `validation_errors=[]`。
- [ ] 检查当前规则是否仍有不需要的 `drop_leaf`。

## 12. 当前验证结论

最近“短线重连接并且杀人后强检”样本已经验证：

```text
NETWORK_RECONNECT：通过
8C03：28 条，持续 +120 slot
9100：1 条，slot=3000
mrpcs_i_vv.data：input/output 均出现
output_groups_valid：全部通过
validation_errors：0
```

当前项目的稳定核心是 **Live 优先、缺失才补、周期保序、未知可回溯**。只要新游戏按本文建立自己的消息规格表和周期模型，就可以复用同一套重放框架。
