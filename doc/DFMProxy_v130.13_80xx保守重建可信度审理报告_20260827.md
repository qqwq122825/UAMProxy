# DFMProxy v130.13 · 80xx 保守重建可信度审理报告

> 日期：2026-08-27  
> 目的：停止“玩家 80xx 全量照录制复放”的宽口径，只允许证据闭环、字段语义和触发时机均已锁定的消息进入自动重建。  
> 本文先给审理结论；代码、提交、tag 和打包在结论确认后处理。

## 1. 审理标准

一个 ID 进入“可信自动重建”必须同时满足：

1. 多账号、多局的正文结构一致；
2. 动态字段的语义和生成公式已经锁定；
3. 首发条件、复发条件和周期已经锁定；
4. 录制短缺时不会靠猜测补出不存在的叶；
5. 同设备重放时不会因重启、当前进程、当前对局或账号状态变化而失真；
6. 已知样本里没有相互冲突的第二形态；
7. Live 原生叶优先，重建只填真正缺失的叶，报告序号按实际新增叶统一后移。

任一项存在反例，该 ID 不进入默认可信组。周期“看起来稳定”本身不足以证明正文可重建。

## 3. 最终分级

### A 级：可进入默认可信自动重建

#### 中央 9 类

`8000 / 8002 / 8003 / 8004 / 800B / 8020 / 8021 / 8025 / 8028`

现有多账号长样本和模型一致，周期分别为：

- 8000、8002、8003、8020：600 slot；
- 8004：300 slot，每档 9 个 subtype；
- 800B：900 slot；
- 8021：首 slot 158，周期 420；
- 8025：连接一次；
- 8028：240 slot。

这 9 类继续使用中央模型，按 `message_id@slot` 判重；8004 额外按 subtype 判重。Live 已有片保留，只补缺片。

#### 800D：仅在严格门槛下进入同设备可信组

800D 的 600-slot 时间尺及 `+0x20 = 1 + cycle×20` 已由多份长样本复证。允许重建的前提：

- 设备指纹严格一致；
- 录制中至少两档，末两档差值恰好 600；
- 只改已确认的轮次字段和目标 slot；
- Live 同身份叶优先。

因此“同设备玩家可信数据”建议先只包含 800D，不把其余 7 类捆进来。

### B 级：机制已验证，但只能独立选择，默认关闭

#### 强检反馈：8C03 / 9100

只在对应下发文件对实际出现后生成：

- 8C03：`mrpcs_i_f + mrpcs_i_j`，120-slot；
- 9100：`mrpcs_i_v_tl + mrpcs_i_vv`，600-slot。

没有武装条件时零生成。它们保持独立开关，适合“只补强检反馈”的用法。

#### 扫描数据：8027 / 8029

已验证的是“扫描波识别、录制波复放和分波周期”，不是“录制正文永远等于重放当下环境”。正文包含进程、Bundle、模块/调用位置，当前运行环境变化会改变原生结果。

建议：

- 单独开关，默认关闭；
- 模板必须至少有完整 W1 和 W2 开扫证据；
- 只循环已经完整录到的波，不按固定名单编新进程；
- 不并入默认可信组；
- Live 漏出时保留 Live，不用邻近录制正文覆盖当前状态。

#### 对局数据：802A / 802B

已确认随进入对局成对出现，但历史样本同连接可出现第二对，而当前“整场 identity 一次”会漏掉第二对。因此保留独立开关，默认关闭；需要按对局门沿而不是固定周期处理后，再升级为默认可信项。

### C 级：固定排除主动重建

| ID | 排除原因 | 处理口径 |
|---|---|---|
| 8007 | 周期稳定，但正文含设备/进程状态向量，字段语义未完全锁定 | 原生 Live 保留；调度器不主动补发、不外推 |
| 800A | 稀疏 900 与 30-slot 密发簇并存，不同账号形态冲突 | 不主动补发，不参与周期就绪 |
| 800C | 不规则测量向量、正文多形态、slot 无稳定周期，部分账号存在高熵区 | 不主动补发、不外推、不做 nearest 替换，不参与周期就绪 |
| 800F | 干净样本全零，异常样本出现非零设备字；形态与状态相关 | 不主动补发 |
| 8023 | 一次性设备相关检测数组，字段语义未锁定 | 不主动补发 |
| 8024 | 字段语义已知；游戏只要求可用的重启时间域，不要求对应最近一次物理重启 | 默认关闭；勾选且模板真实存在时可继承录制 epoch |
| 802C | 周期和推进公式较清楚，但依赖录制时间元数据及连接四步链 | 默认关闭；勾选且时间对/链条件齐全时可按公式推进，否则只复放真实录制叶 |

这里需要特别区分：`800D/8024/802C` 不应作为一个无条件全开的“三类组合”。800D 的轮次公式最清楚；8024/802C 的时间关系可复用，但仍应逐项默认关闭，并受录制时间对和连接链条件约束。设备后来真实重启本身不再构成停发理由。

## 4. 推荐的配置结构

开启“重建模式”后，显示以下独立多选：

1. **中央 9 类**：默认开；
2. **同设备可信数据（仅 800D）**：默认关；
3. **强检反馈（8C03/9100）**：默认关；
4. **对局数据（802A/802B）**：默认关；
5. **扫描数据（8027/8029）**：默认关。

固定排除列表在界面直接展示：

`8007 / 800A / 800C / 800F / 8023 / 8024 / 802C`

8028 已属于中央 9 类，不再重复放进扫描或玩家组。

只勾“强检反馈”时，中央 9 类、800D、802A/B、8027/29 都不生成；实际下发满足武装条件后只补 8C03/9100。

## 5. 自动结束与周期就绪口径

“80xx 完整度 + 周期就绪”应按当前勾选的重建集合动态计算，不能继续固定等待旧的 7 项：

- 中央 9 类：检查 9 类覆盖和 8004 的 9 subtype；
- 800D 被勾选：要求两档且差 600；
- 8027/8029 被勾选：要求第一完整波闭合并见到第二波开扫；
- 802A/802B 被勾选：要求至少见到一组成对数据，不作为周期项；
- 800A、800C 等固定排除项不计入完整度分母，也不阻塞周期就绪。

这能避免录制因为等待一个本来就不准备重建、且永远没有稳定周期的 800C/800A 而持续不结束。

## 6. 实现时的硬保护

确认报告后，代码建议同时加两层保护：

1. 调度规划层只从白名单生成候选；
2. 最终注入层再次校验白名单，防止旧配置或缓存模板把排除 ID 带回来。

固定排除 ID 的 Live 原生数据保持原样进入正常路径；重建器不生成、不外推、不用录制模板覆盖。所有真实新增叶统一经过报告序号偏移器，使当前报告及后续报告的计数连续后移；`pass_live` 或判重未新增时不偏移。

## 7. 审理结论

严格口径下：

- 默认可信自动重建：中央 9 类；
- 同设备可信扩展：仅 800D，且必须满足设备匹配与两档 600-slot 证据；
- 强检、对局、扫描：独立、默认关闭，其中对局和扫描不并入默认可信组；
- 8007、800A、800C、800F、8023：默认固定排除主动重建；8024/802C 默认关闭但保留条件开关；
- 800C 明确退出补发、外推、邻近替换和周期就绪统计。

这套口径宁可少补，也不根据不确定数据编造正文。

## 8. 给其他 AI 的独立评测题：为何暂不重建这 7 个 ID

请其他评测者不要只看消息名称或单个账号的周期数字，而是逐项回答“正文是否能从已知字段确定地生成下一条”。评测基准是：同设备、跨账号、录制结束后延长重放、设备可能重启、Live 可能漏出这几种组合都要成立。

### 8007：周期像确定，正文语义仍未闭环

- 多份样本看到 `60/660/1260...` 的 600-slot 尺；
- 但正文是短系统/设备状态向量，含设备相关字段；
- 当前实现主要是冻结录制正文，而不是依据已锁定字段公式重建；
- 游戏进程、系统状态或设备环境变化时，冻结旧向量可能与原生新向量不一致。

**评测问题：** 是否有跨账号、跨进程、跨周期的字段差分，能证明每个动态字段都应保持录制值？若没有，8007 只能作为录制叶复放，不能列入自动外推组。

### 800A：同一 ID 存在互相冲突的时间形态

- 干净长样本出现 `30→930` 的稀疏形态；
- 130.12 第二账号出现大量 `30-slot` 密发簇，并夹有长空档；
- 历史封禁样本也出现另一种密发形态；
- “固定900”会把30-slot簇误判成周期，“固定30”又会制造大量原生不存在的后续叶。

**评测问题：** 在没有当前账号形态识别器、没有至少三个簇和两个近似一致簇间隔前，凭什么选择900、30或簇间隔？只要答案依赖猜测，800A 就应固定排除主动重建。

### 800C：高熵测量向量，没有稳定周期或唯一生成公式

- 130.12 第一账号10条 slot 全部不同；第二账号29条 slot 全部不同；
- 两账号的 slot 序列、间隔和出现密度显著不同；
- 正文分别出现多种状态形态，存在浮点/测量区变化；
- 现有代码没有能从时间、设备指纹或上一条正文推导下一条正文的公式。

**评测问题：** 若只拿最近一条或邻近模板进行替换，如何证明测量值仍对应重放时刻？在无法给出确定误差界的情况下，800C 应退出补发、外推和周期就绪统计。

### 800F：干净空壳与异常设备字是两种画像

- 干净样本常见全零空壳；
- 异常/封禁样本出现非零设备字；
- 该差异与运行状态、检测阶段相关，不能依据 ID 和周期单独选择正文；
- 即使看到900-slot，也只能证明发送时机，不能证明下一条正文内容。

**评测问题：** 重放前如何知道当前会话属于全零画像还是非零画像？没有状态分类器时，固定复制任一形态都会引入错误。

### 8023：一次性设备检测数组，字段语义未锁

- 通常连接首段出现一次，正文含设备相关数组/数值；
- 多份样本数量少，缺少跨设备和跨账号的字段因果验证；
- 它不是可由周期推导的计数型消息；
- 重连是否应重新生成，取决于客户端检测阶段，当前模型未覆盖全部情况。

**评测问题：** 是否能证明数组每一项在同设备重放时保持不变，并能判断新连接是否应再次发送？若两点任一点缺证，8023 只保留录制原叶，不由重建器主动创建。

### 8024：语义清楚，但“同设备”不等于“同一次开机域”

- `+0x20` 属于设备开机epoch，设备关机重启后会变化；
- `+0x24` 属于更长期的落地/安装epoch；
- 当前录制值在同一设备重放时可能跨越新的设备开机周期；
- 只按录制值发送，会出现“字段语义正确、会话时序错误”的情况。

**评测问题：** 重放开始前能否获得当前 Live 8024 的开机域锚点并确认与录制一致？没有锚点时，继续发录制8024的依据是什么？因此8024不进入默认可信重建组。

### 802C：公式已知，但依赖多个外部锚点和连接链

- `+0x20` 依赖8024开机epoch、墙钟和 `recorded_at`；
- `+0x24/+0x28` 依赖同连接的四步链，连接首包与中途切片的行为不同；
- 设备重启、系统拨钟、缺失时间元数据或中途录制都会改变可重建条件；
- 只有一档时不能可靠编出下一档，旧模板也无法还原“新开机+小uptime”的原生形态。

**评测问题：** 是否同时具备当前设备时间锚、录制时间元数据、连接首包链和重启状态？缺任一项时，应保留Live或录制原叶，而不是套公式生成新叶。

### 七个 ID 的共同结论

这七个 ID 并非“永远不发送”，而是：

1. 录制中真实出现的叶可以按原生路径保留；
2. Live 真实出现时优先保留 Live；
3. 重建器不主动创建、不按固定周期外推、不用邻近模板猜正文；
4. 只有未来补齐状态分类器、设备开机域锚点、测量向量模型和充分跨账号样本后，才重新申请进入白名单。

评测者若主张把其中任何一个放回自动重建组，需要同时给出：字段级生成公式、触发/复发条件、跨账号证据、设备重启边界和失败时的回退行为。仅有“次数多”“周期看起来像600/900”不构成放行依据。

### 9.2 风险二分（用户补充，请 OpenAI 讨论）

七个 C 级不要捆成同一类「都不可信」。用户与 Cursor 倾向拆成两层：

| 组 | ID | 卡点性质 | 跨账号外扩可信度 |
|---|---|---|---|
| **A. 内容/形态未闭环（核心低可信）** | `8007 / 800A / 800C / 800F / 8023` | 重建要**周期 + 正文**才能外扩；账号间形态/画像/字段因果冲突或未锁 | **很低** |
| **B. 时间锚未闭环（公式偏已知）** | `8024 / 802C` | 时间尺与推进关系相对清楚；难在**开机域 / Live 锚点 / 连接链 / recorded_at**，不是「每个账号正文算法完全不同」 | **条件满足时可讨论**；缺锚点时仍不可默认可信 |

分项说明（A 组为何才是跨账号重建主风险）：

| ID | 为何跨账号外扩可信度低 |
|---|---|
| **8007** | 周期像 600，正文含设备/进程状态向量，字段语义未完全锁定；不能拿 A 账号正文硬套 B 账号 |
| **800A** | 同一 ID 出现稀疏 `30,930` 与 30-slot 密发簇等冲突形态；**周期本身就不统一** |
| **800C** | 无稳定周期，测量向量高熵；两账号 slot/间隔/密度显著不同，整叶几乎条条不同 |
| **800F** | 干净全零壳 vs 异常非零设备字，画像分裂；跨账号猜会选错壳 |
| **8023** | 一次性设备检测数组，跨账号字段因果未验证；不知「该不该再发 / 发什么」 |

| ID | 为何更像时间问题而非「内容算法全乱」 |

## 9.8 【用户补充前提 + OpenAI 修正】8024/802C 不要求反映真实本次重启

### 用户补充的协议口径

游戏侧只要求 8024 中存在一个可用的“重启时间/开机时间域”，并不要求它真实对应设备最近一次物理重启。设备录制后即使重启，重建仍可沿用录制时的旧开机时间。

### 【OpenAI】接受并修正前述结论

**同意用户口径。第 9.7.4 将 Live 开机域锚点设为硬门槛过严，本节取代该门槛。**

在这个协议前提下：

- `8024[+0x20]` 可直接继承录制的开机 epoch；
- 设备后来是否真实重启不再作为停发条件；
- 不需要等待当前 Live 8024 来证明开机域一致；
- `8024[+0x24]` 继续保持录制的落地/安装 epoch；
- 重点从“时间是否真实”调整为“8024 与 802C 的组合是否自洽”。

推荐关系继续使用已经验证的模型：

```text
virtual_boot_epoch = recorded_8024[+0x20]
rebuilt_802C[+0x20]
    = recorded_802C[+0x20] + (replay_now - recorded_at)

因此：
virtual_boot_epoch + rebuilt_802C[+0x20] ≈ replay_now
```

这里的 `virtual_boot_epoch` 是继承的录制开机域，不宣称等于设备最近一次真实开机时间；只要它与持续增长的 802C 保持一致即可。

### 修正后的 8024/802C 放行条件

```text
8024放行 = 单项勾选 ∧ 设备门通过 ∧ 模板真实存在8024

802C原叶复放 = 单项勾选 ∧ 设备门通过 ∧ 模板真实存在802C

802C时间推进 = 上述条件
             ∧ recorded_at有效
             ∧ 录制8024/802C时间对有效

802C链推进 = 上述条件
           ∧ 当前连接链状态可确定
```

Live 8024/802C 仍然优先；Live 已出现同身份叶时，模板不重复补同一片。但 Live 不出现不再等于“缺开机域锚点”，录制时间对本身就是重建采用的虚拟时间锚。

### recorded_at 或连接链信息不完整时

- 缺 `recorded_at`：只发送模板中真实录到的 802C 原叶，不生成时间外推档；
- 链起点不明确：保持录制原叶的链字段，不主动续编后继链；
- 只有一档802C：只复放这一档；仍需两档600-slot证据才讨论周期延长；
- 任何情况下都不虚构模板中没有的8024形态。

### 对 A/B 分组的影响

B组 `8024/802C` 不再描述为“必须有当前 Live 开机域锚点才可信”，而调整为：

> **字段关系和推进公式较明确，可继承录制的虚拟开机域；主要门槛是录制时间元数据与802C连接链是否足以支持推进。**
