## 1. 读取约定

Type9 解密明文中的常见层级：

```text
0x010A001B                         批量容器，不是 messageId
└─ 0x0102000A                     带 messageId 的二进制叶子
   ├─ +0x0A BE32                  recordSequence
   ├─ +0x16 BE16                  messageId
   └─ +0x20                       messageId 专属正文
```

根叶子的 `path=[]` 和容器叶子的 `path=[N]` 使用同一套语义。当前热规则匹配键为：

```text
(recordCode, messageId, actualLength)
```

通配长度的 `replace_template_nearest` 按 `(recordCode, messageId)` 从干净池选择长度最近的模板，并在变长时同步重建容器、Type9 和 01 外层长度及 CRC。

| `0xFFFB` | tersafe周期状态 | 包含tersafe及报告计数 | `+0x28` 为动态报告计数 | 保留Live动态字段 | 检测状态候选 |

## 3. `0x0207`：疑似缺页数/异常页计数

固定结构：

```text
recordCode = 0x0102000A
messageId  = 0x0207
length     = 116
```

在“未快速封禁”和“快速封禁”样本对照中，次数同为3条，但出现两个稳定的零转非零字段：

| 完整叶子偏移 | 正文偏移 | 对照A | 对照B |
|---:|---:|---:|---:|
| `0x48` | `+0x28` | 0、0、0 | 13、13、28 |
| `0x50` | `+0x30` | 0、0、0 | 1、1、1 |

当前把 `+0x28` 记为“疑似缺页数/异常页数量”，把 `+0x30` 记为“疑似异常存在标记”。这是根据多样本差分形成的候选命名，尚未从客户端构造函数或正式协议字段名确认。

当前规则不替换整条116字节叶子，只保留Live主体并清零两个候选字段：

```json
{
  "id": "0207-zero-anomaly-counters",
  "match": {
    "record_code": "0x0102000A",
    "message_id": "0x0207",
    "length": 116
  },
  "action": "patch_live",
  "patches": [
    {"offset": "0x48", "hex": "00000000"},
    {"offset": "0x50", "hex": "00000000"}
  ]
}
```

## 4. `0x2000`：正常存在的周期模块检测结果

### 4.1 正常原始录制

来源：

```text
数据/121/2/01RecordPackets/test_01_message_leaves_20260805_051600_348198.jsonl
```

共发现10条正常 `0x2000`：

```text
report = 3, 27, 43, 54, 64, 77, 87, 97, 106, 115
长度   = 44（10/10）
容器内 = 8
根叶子 = 2
```

除实时 `recordSequence` 外，10条正文一致，结果区为空/零值：

```hex
00000001002C0102000A0000001100000000000000162000200F000234560001000000000000000000000000
```

这证明 `0x2000` 不是出现插件后才新增的消息，而是正常周期消息。

### 4.2 插件注入重放

来源：

```text
数据/121/5:重放 插件注入/01ReplayAnalysis/run_20260805_175511_161476/01_replace_events.jsonl
```

该样本共出现17条 `0x2000`：

```text
长度80            = 17/17
含dfm_cn_yy.dylib = 17/17
```

模块名使用 XOR `0xB6` 编码，解码文本包括：

```text
dfm_cn_yy.dylib
com.tencent.tmgp.dfm
```

因此当前语义记录为：

```text
正常结果：0x2000/44，结果为空
命中结果：0x2000/80，结果携带模块名和关联身份
```

### 4.3 当前处理

不删除 `0x2000`，保留消息节奏和实时叶子序号，正文从干净池取得：

```json
{
  "id": "2000-clean-module-report",
  "match": {
    "record_code": "0x0102000A",
    "message_id": "0x2000",
    "length": "*"
  },
  "action": "replace_template_nearest"
}
```

当前注入样本回溯结果：

```text
0x2000替换       17/17
叶子长度         80 -> 44
Type9明文CRC     17/17通过
01外层CRC        17/17通过
根/容器结构回验  17/17通过
```

## 5. 插件路径不只出现在 `0x2000`

`dfm_cn_yy.dylib` 在当前注入样本还出现于以下记录：

| 类型 | Live长度 | 干净池长度 | 说明 |
|---|---:|---:|---|
| `0x0102000A / messageId=0x1105` | 125 | 93 | 3个报告出现完整路径；该ID还有其他正常长度和正常内容 |
| `recordCode=0x01122360`，无messageId | 276 | 251 | 1个报告出现明文完整路径 |
| `recordCode=0x01122332`，无messageId | 281 | 当前玩家池无模板 | 2个报告出现明文完整路径 |

当前处理区分为：

```text
0x2000：按ID使用干净模板；正文命中 dfm_cn_yy / mtxdfm 等则改删叶
0x1105：按ID使用最近长度干净模板，保留Live前36字节；路径命中插件名则删叶
0x01122360/0x01122332：无messageId，由内容黑名单在正文命中插件名或路径时删叶
```

`0x1105`完整规则回溯：

```text
Live 0x1105          17条
替换为干净93字节     17/17
Live内部枚举序号保留  17/17
Type9/01/CRC回验      17/17通过
```

同时启用 `0x2000` 和 `0x1105` 规则后，两个messageId中的
`dfm_cn_yy.dylib` 均已消失；剩余命中只来自 report 21、75 的
`0x01122360`、`0x01122332` 无messageId记录。

不要把 `0x01122360`、`0x01122332` 写进 `messageId` 表；它们是 `recordCode`。

## 7. 维护要求

以后分析新ID时，在本报告补充以下内容：

1. `recordCode`、`messageId`、根/容器形态；
2. 正常和异常样本数量及全部长度；
3. 稳定字段偏移、字节序和观察值；
4. 字段语义的证据等级；
5. 应保留Live、定点修改、同长度模板替换还是最近长度模板替换；
6. Type9 CRC、容器长度、01外层CRC和回环验证结果。

任何“疑似”字段在找到构造函数、字段名或更多独立样本前，都继续保留候选标签。

## 8. 内容黑名单与进程一条一叶

`0x8027`、`0x8029`、`0x9000` 都是一条叶子一个对象，不是一条消息里打包很多个进程。同一条 `01 0A 00 09` 可以有多片叶子，黑名单只删命中的那一片，再重建父容器。

默认词（明文和 XOR-B6 都扫，大小写不敏感）：

```text
com.mtx.mtxdfm  mtxdfm  dfm_cn_yy
dopamine  多巴胺
trollstore  巨魔
filza  文件管理器
sileo  roothide  zebra  appstoreplus
```

优先级：内容黑名单删叶 > `tfp_called` > 普通热规则。脏 `0x8027` 不再换成另一条相近长度的干净进程。

取消 hook 后不要从录制补 80xx 叶子。`0x8023` / `0x1100` 末尾是系统版本，不是旧 09/10 报告里的检测开关。
