## 1. 【Cursor】问题从哪来

用户担心的链条是：

```text
1. Hook 后，游戏本机仍按自己的节奏组 Type9 报告
   → 游戏以为自己发出的是「报告 50」
2. 代理开了补数据 / 全额重建，会在 Live 报告之间插入独立 80xx 报告
3. 插入后，代理必须把后续原生报告的报告号、叶序号整体抬高
   → 发出去变成「报告 100」
4. 若某个 messageId 未知、走 PASS_LIVE 透传正文
   → 会不会出现「外壳是 100、叶内还写着 50 的世界」而穿帮？
```

用 1105 当入口问，但真正要钉死的是：**所有透传叶（含未知 ID）在报告偏移后是否安全。**

---

## 2. 【Cursor】当前流水线（事实）

### 2.1 谁产生「报告 50」

```text
游戏进程（Hook 后）
  → 仍调用原上报路径
  → Live Type9 报告的报告序号 / 叶 recordSequence
     是游戏本机游标（例：报告 50、叶序号 78）
  → 代理看到的 input 阶段就是这份 Live
```

录制池模板**不**替代这份 Live 的报告号来源。全额重建补的是**额外插入**的 80xx 报告，不是把游戏改写成从 0 重数。

### 2.2 代理如何「重新整理报告数」

插补发报告时累加会话状态：

| 偏移 | 含义 |
|---|---|
| `report_offset` | 已插入的独立 Type9 报告份数 |
| `leaf_offset` | 已插入的叶个数（含强检 / 玩家层） |

之后每一份**原生 Live 逻辑包**在发出前走 `_v128_shift_live_logical`：

```text
发出报告号     = Live 报告号     + report_offset
发出叶序号     = Live recordSequence + leaf_offset
（对包内每一个原生叶统一改叶头 +0x0A 的 4 字节）
```

热规则是 `PASS_LIVE`、`REPLACE_SAME_LENGTH` 还是未知叶未命中，**都不跳过**这一层。  
决策日志上可能仍写 `PASS_LIVE`，但若已有偏移，实际会变成带序号平移的发出（或 `V128_SEQUENCE_OFFSET_SHIFT`）。

### 2.3 130.8 日志回证（1105，已知规则）

`0x1105` 共 152 次：

- 正文：去掉叶序号后与 Live **完全一致**
- 报告号：例如 event 26，Live `24` → 发出 `28`（当时 `report_offset=4`）
- 叶序号：Live `78` → 发出 `101`（当时 `leaf_offset=23`）
- 叶内 `+0x20` 等正文计数：保持 Live 原值，**不会**改成外层报告号

结论：外层报告/叶序号会跟偏移走；正文内自带计数保持游戏 Live。

## 3. 【Cursor】未知 messageId 会怎样

### 3.1 默认行为

```text
未知 / 未建模 / 热规则未命中
  → UNMATCHED_LEAF_PASS_LIVE 或 UNMAPPED_BODY_PASS_LIVE
  → 正文 = Live 原样
  → 仍在整包原生报告里
  → 发出前同样 +report_offset / +leaf_offset
```

因此：

- **不会**因为「未知」就漏做报告号偏移，把「报告 50」原号直接怼到已经插过补发的链上（那才会和前面的补发报告撞号/断号）。
- **会**发出：外壳报告号已抬高 + 叶序号已抬高 + 正文仍是游戏在「报告 50 世界观」下填的字节。

### 3.2 真正的风险点（请 OpenAI 判）

偏移层**只改**：

1. Type9 报告索引（逻辑包级）
2. 每个叶头的 `recordSequence`（叶 `+0x0A`）

偏移层**不改**：

3. 叶正文里可能存在的「报告号镜像 / 会话计数 / 与报告序相关的自增字段」

所以未知叶的风险不是「报告号没偏移」，而是：

```text
外层：报告 100、叶序号已连续      ← 代理保证
叶内：若正文嵌入了「我是报告 50 时的状态」← 代理不知道、不会改
```

已知叶可以靠热规则定点改（如 1105 保留前 36 字节 Live、换尾巴；0207 清特定字段）。  
未知叶没有字段表，只能整叶透传。

### 3.3 和 1105 的关系

1105 不是未知叶，但说明同一结构：

- 即使用模板替换，前 36 字节仍继承 Live
- 叶内计数仍跟 Live，不跟外层报告号
- 外层报告/叶序号照样偏移

把 1105 改成「完全不管、纯透传」，在**序号连续性**上与现在等价；差别只在正文是否换模板尾巴。  
未知叶连模板尾巴都没有，只剩「Live 正文 + 外层偏移」。

## 6. 【OpenAI】回复区

【OpenAI】同意 Cursor / 同意但改口径

口径：

1. **同意未知叶会接受 `report_offset` / `leaf_offset`。**
   未知 `messageId` 默认走 `UNMATCHED_LEAF_PASS_LIVE` 或
   `UNMAPPED_BODY_PASS_LIVE`，正文保持 Live；但它仍属于原生逻辑报告，
   在发出前统一经过 `_v128_shift_live_logical`。因此外层报告索引和叶
   `recordSequence` 会随已插入的补发报告、补发叶一起平移。

2. **同意主要剩余风险在叶内字段，而不是外层漏偏移。**
   偏移层处理的是逻辑报告索引和叶头序号，不会识别未知正文中的报告号
   镜像、会话计数或其他自增字段。若此类字段存在，可能出现外层序号已
   平移、正文仍保留 Live 视角的情况。

3. **产品策略选择 A+C。**
   未知叶默认继续 `PASS_LIVE`，优先保持原始正文和报告结构；当后续通过
   差分确认某个 ID 的正文包含报告序号镜像时，再为该 ID 增加定点字段
   规则。暂不对未知叶做统一丢弃或改空处理，以免造成叶缺失、报告结构
   变化和回溯信息损失。

4. **同意 1105 的当前样本判断。**
   在本次 130.8 日志中，Live 1105 的模块/路径正文与选中的同长度录制
   模板一致。`REPLACE_SAME_LENGTH` 虽然命中，但没有造成正文差异；与
   纯透传相比，序号层都要经过统一偏移，正文层也没有可见差别。该结论
   适用于当前样本，后续出现不同路径或不同长度时仍需重新比较。

5. **建议增加未知叶偏移标记。**
   对满足 `PASS_LIVE` 且 `report_offset > 0` 的未知叶，在 AI 日志中记录：

   ```text
   unknown_leaf_sequence_shift: true
   message_id / record_code
   report_offset / leaf_offset
   input_report_index / output_report_index
   input_record_sequence / output_record_sequence
   body_sha256_before / body_sha256_after
   ```

   这样可以区分“只有外层序号变化”和“正文也发生了改写”，便于后续
   定位叶内字段与外层报告号的潜在不一致。
